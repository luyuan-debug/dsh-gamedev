# 发布维护

本页供发布新版本的维护者使用。下载安装插件，请阅读 [安装指南](SETUP.md)。

## 准备版本

1. 完成源码构建和测试，更新使用说明、版本记录及第三方许可。
2. 用最终安装包测试安装、启动、游戏修改、重启和卸载，记录软件版本、结果和未测项。
3. 为安装包、源码和公开测试摘要生成 SHA-256。测试记录必须对应实际发布的文件。
4. 编写发布说明：先讲用户能做什么、此次变化、安装方式和已知限制，详细实现与测试数据放到对应文档。

包中不附带 Godot、DSH、模型账户或个人游戏。单独安装的第三方软件遵循各自许可，见 [第三方声明](../THIRD_PARTY_NOTICES.md)。

## 检查公开文件

将要发布的文件复制到一个干净目录，再运行：

```sh
python3 -B scripts/scan_publication.py /absolute/path/to/clean-public-export
```

扫描后逐项审阅结果和文件清单。已有 Git 仓库可使用 `--tracked` 检查已跟踪文件：

```sh
python3 -B scripts/scan_publication.py . --tracked
```

扫描器只报告结果，不会修改或脱敏文件。它检查常见的密钥、私人路径、缓存和非发布文件，但无法识别所有私人内容；Git 历史需要另外审阅。截图、音频和其他二进制文件需单独检查内容、元数据与使用权。

公开附件中不要包含账户配置、令牌、带鉴权参数的 URL、原始模型对话、个人路径、已有游戏或完整本地日志。测试摘要应只保留复查所需的信息。

## 上传与后续修订

发布前核对仓库简介、README、文档链接、提交说明、发布标题、下载文件名和许可。提交说明用简洁的动作描述改动，例如“补充安装与故障排查说明”，避免沿用开发阶段的编号和汇报措辞。

已经发布的标签、安装包及其校验值应保持对应。只修订说明时，可以更新 `main` 和发布页；若修改安装包内容，应发布新版本并重新测试，不用同名文件替换旧包。

GitHub Actions 运行构建和源码测试，不使用模型账户，也不启动真实 DSH 或 Godot。发布页应分别说明源码测试和应用测试的范围。
